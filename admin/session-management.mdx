Nexxus tracks every browser tab that opens your deployment as an individual session. Each session has a stable ID, carries full device and network metadata, is continuously updated via a heartbeat, and can be silently terminated by an administrator at any time. This page documents the full technical implementation — from the moment a visitor loads the page to the moment their session is closed.

---

## The `VisitorSession` Data Structure

Every session is stored as a `VisitorSession` object, defined identically on both the server (`server.ts`) and the admin console component (`AdminConsole.tsx`).

<ResponseField name="id" type="string" required>
  Unique session identifier. Generated by the client as `session_{timestamp}_{random}` (e.g. `session_1703000000000_abc123ef`) and stored in `sessionStorage`. The server may also generate a fallback ID in the format `sess_{timestamp}_{random6}` if the client does not supply one.
</ResponseField>

<ResponseField name="ip" type="string" required>
  The visitor's IP address, extracted from the `x-forwarded-for` HTTP header (first entry) or the raw socket address. IPv6-mapped IPv4 addresses (e.g. `::ffff:192.168.1.1`) are normalised to plain IPv4.
</ResponseField>

<ResponseField name="device" type="string" required>
  Human-readable device name detected from the User Agent and client environment — e.g. `Windows PC`, `Apple iPhone`, `Samsung Galaxy Device`. See [Device Detection](#device-detection) below.
</ResponseField>

<ResponseField name="browser" type="string" required>
  Browser name and major version, e.g. `Chrome 120`, `Edge 119`, `Firefox 121`. Detected client-side by `detectClientDevice()` and sent with the session open payload.
</ResponseField>

<ResponseField name="os" type="string" required>
  Operating system string, e.g. `Windows 11 / 10`, `macOS`, `iOS`, `Android`, `ChromeOS`. Detected by both the client and server independently; the client-supplied value takes precedence.
</ResponseField>

<ResponseField name="openedAt" type="number" required>
  Unix timestamp in milliseconds when the session was created by `POST /api/telemetry/open`.
</ResponseField>

<ResponseField name="closedAt" type="number | null" required>
  Unix timestamp in milliseconds when the session was closed, or `null` if the session is still active.
</ResponseField>

<ResponseField name="lastHeartbeat" type="number" required>
  Unix timestamp of the most recent heartbeat received from the client. Used by the server background job to detect dead sessions.
</ResponseField>

<ResponseField name="durationSeconds" type="number" required>
  Running total of elapsed seconds since `openedAt`. Recalculated on every heartbeat as `round((now - openedAt) / 1000)`, with a minimum of `1`.
</ResponseField>

<ResponseField name="status" type='"online" | "closed"' required>
  Current session state. Set to `online` on creation and on every heartbeat. Set to `closed` by an explicit close call, the 25-second inactivity timeout, or on server restart.
</ResponseField>

<ResponseField name="currentGame" type="string">
  The visitor's last reported activity string, e.g. `Playing 1v1.LOL` or `Browsing Library`. Updated on every heartbeat. Defaults to `Viewing Library` when the session is first created.
</ResponseField>

<ResponseField name="screen" type="string">
  Screen resolution string in `{width}x{height}` format, e.g. `1920x1080`. Detected client-side via `window.screen`.
</ResponseField>

<ResponseField name="language" type="string">
  Browser locale from `navigator.language`, e.g. `en-US`. Defaults to `en` if not available.
</ResponseField>

<ResponseField name="kicked" type="boolean">
  Set to `true` by the server when an admin issues a kick command. Cleared back to `false` on the next heartbeat after the client receives the kick signal. See [Kick Mechanism](#kick-mechanism).
</ResponseField>

## Session Lifecycle

<Steps>
  <Step title="Page initialisation — session open">
    When a visitor loads Nexxus, `telemetry.init()` runs immediately. It checks `sessionStorage` for an existing `nexxus_session_id`. If found, that ID is reused (supporting page refreshes within the same tab). If not, a new ID is generated as `session_{Date.now()}_{random8}` and saved to `sessionStorage`.

    The client then calls `POST /api/telemetry/open` with a JSON payload containing the session ID, device name, OS, browser, screen resolution, language, and initial activity state. The server creates a new `VisitorSession` record and persists it to `.cache/sessions.json`.
  </Step>
  <Step title="Heartbeat loop — session keep-alive">
    Every **2.5 seconds**, the client sends `POST /api/telemetry/heartbeat` with the session ID and the current `currentGame` string. The server responds with `{ success: true, duration, kicked }`.

    On each heartbeat, the server:
    - Updates `lastHeartbeat` to the current time.
    - Resets `status` to `online`.
    - Recalculates `durationSeconds`.
    - Updates `currentGame` if provided.

    If `kicked` is `true` in the response, the client fires the kick flow immediately (see [Kick Mechanism](#kick-mechanism)) and the `kicked` flag is cleared to `false` on the server.
  </Step>
  <Step title="Activity updates — game tracking">
    When a visitor launches a game, `telemetry.updateGame(gameTitle)` is called. This sets the local `currentGame` string to `Playing {gameTitle}` and immediately sends an out-of-band heartbeat to notify the server. When a visitor exits a game, `updateGame(null)` sets the state back to `Browsing Library`.
  </Step>
  <Step title="Page unload — session close">
    When the visitor closes the tab, navigates away, or the browser fires `beforeunload` or `pagehide`, the client calls `POST /api/telemetry/close` using `navigator.sendBeacon` (or a `fetch` with `keepalive: true` as a fallback). The server sets `status` to `closed`, records `closedAt`, and recalculates the final `durationSeconds`.
  </Step>
  <Step title="Server-side timeout — dead session cleanup">
    A background job runs every **10 seconds** on the server. Any session with `status === 'online'` whose `lastHeartbeat` is more than **25 seconds** in the past is automatically marked as `closed`, with `closedAt` set to the last known heartbeat time.
  </Step>
  <Step title="Server restart — session recovery">
    On startup, the server loads `.cache/sessions.json`. Any session that was `online` at the time of the previous shutdown is immediately marked `closed` with `closedAt` set to its `lastHeartbeat` value. This prevents phantom "online" sessions persisting across restarts.
  </Step>
</Steps>

## Session ID Persistence

The client session ID is stored in the browser's `sessionStorage` under the key `nexxus_session_id`.

<Note>
  `sessionStorage` is scoped to a single browser tab and survives page refreshes within that tab, but is cleared when the tab is closed. This means each new tab opened to Nexxus creates a brand-new session, while refreshing an existing tab reuses the same session ID — keeping the session log clean and accurate.
</Note>

When an admin clicks **CLEAR** in the console, the server deletes all session records **and** the client calls `telemetry.resetSession()`, which removes `nexxus_session_id` from `sessionStorage` and clears the in-memory session ID. The next page interaction creates a completely fresh session.

## Server-Side Storage

Sessions are held in a `Map<string, VisitorSession>` in the Node.js process memory for fast lookups and updates.

<CardGroup cols={2}>
  <Card title="Memory Cap" icon="memory">
    The server retains only the **last 500 sessions** when persisting to disk. Older sessions beyond this limit are dropped from the persisted snapshot. The in-memory map may temporarily hold more until the next persist cycle.
  </Card>
  <Card title="Disk Persistence" icon="hard-drive">
    After every state change (open, heartbeat when kicked, close, kick, or clear), the server writes the session list asynchronously to `.cache/sessions.json`. This file is read on startup to restore the session history across restarts.
  </Card>
</CardGroup>

<Warning>
  Sessions are stored in process memory and a local JSON file. They are not stored in an external database. If the `.cache/` directory is deleted or the server is restarted after a crash, any sessions not yet flushed to disk may be lost. For production deployments with strict audit requirements, consider periodically exporting logs via the **Export JSON** button in the console.
</Warning>

## Kick Mechanism

The kick system allows an administrator to silently return one or more visitors from their current game back to the Nexxus home page — with no alert, banner, or visible interruption shown to the visitor.

### Issuing a Kick

The admin calls `POST /api/telemetry/kick` with one of the following request bodies:

<CardGroup cols={3}>
  <Card title="Kick by Session ID" icon="fingerprint">
    `{ "id": "session_1703..." }` — targets exactly one specific session.
  </Card>
  <Card title="Kick by IP Address" icon="globe">
    `{ "ip": "192.168.1.5" }` — kicks all active sessions sharing that IP address.
  </Card>
  <Card title="Kick All" icon="user-x">
    `{ "all": true }` — kicks every session currently with `status === 'online'`.
  </Card>
</CardGroup>

The server sets `session.kicked = true` on the targeted session(s) and responds with `{ success: true, kickedCount }`. From this moment, the kick is "queued" — it does not act instantaneously on the client.

### Client-Side Delivery

Within **2.5 seconds** (the heartbeat interval), the targeted visitor's browser receives `{ kicked: true }` in the heartbeat response. The `TelemetryClient` then:

1. Resets `currentGame` to `Browsing Library`.
2. Calls all registered `onKick` callbacks.
3. Dispatches a `nexxus:silent-kick` custom DOM event on `window`.

The application listens for this event and silently exits fullscreen mode, then navigates the user back to the home page. The visitor sees no error message, notification, or explanation — they are simply returned to the library view.

The `kicked` flag on the server is cleared to `false` on the same heartbeat that delivers the signal, preventing the kick from firing again on the next cycle.

<Note>
  Kicks only affect active sessions. A session with `status === 'closed'` cannot be kicked. The **KICK ALL** button in the console header confirms this before proceeding, and the Kick Action column in the session table shows `OFFLINE` for closed sessions rather than a kick button.
</Note>

## Device Detection

Nexxus uses a two-layer detection strategy. The **client** runs `detectClientDevice()` from `src/utils/telemetry.ts` and sends its findings to the server with the session open payload. The **server** runs `parseUserAgentDetails()` against the HTTP `User-Agent` header as a fallback — the client-supplied values take precedence.

### `detectClientDevice()` — Client-Side

The client function (`src/utils/telemetry.ts`) inspects `navigator.userAgent`, `navigator.platform`, `navigator.maxTouchPoints`, `window.screen`, and `navigator.language` to build a `ClientDeviceInfo` object.

**Operating System Detection:**

| Detected OS | Trigger Condition |
|---|---|
| `iOS` | UA contains `iPhone` |
| `iPadOS` | UA contains `iPad`, or `platform === 'MacIntel'` with `maxTouchPoints > 1` |
| `macOS` | UA contains `Macintosh` or `Mac OS X` |
| `Windows 11 / 10` | UA matches `Windows NT 10.0` |
| `Windows` | UA contains `Windows` (other versions) |
| `Android` | UA contains `Android` |
| `ChromeOS` | UA contains `CrOS` |
| `Linux` | UA contains `Linux` |

**Device Name Detection (client-side extended):**

| Device Name | Condition |
|---|---|
| `Apple iPhone` | iOS detected |
| `Apple iPad` | iPadOS detected |
| `Apple Mac / MacBook` | macOS detected |
| `Windows PC` | Windows detected |
| `Samsung Galaxy Device` | Android + UA matches `samsung` or `sm-` |
| `Google Pixel Device` | Android + UA matches `pixel` |
| `Android Phone / Tablet` | Android, no Samsung or Pixel match |
| `Chromebook` | ChromeOS detected |
| `Linux Workstation` | Linux detected |
| `Desktop PC` | Default fallback |

**Browser Detection (client-side, with version number):**

| Browser | UA Pattern | Example Output |
|---|---|---|
| Microsoft Edge | `Edg/` | `Edge 120` |
| Opera | `OPR/` | `Opera 106` |
| Google Chrome | `Chrome/` | `Chrome 120` |
| Mozilla Firefox | `Firefox/` | `Firefox 121` |
| Apple Safari | `Safari/` + `Version/` | `Safari 17` |

### `parseUserAgentDetails()` — Server-Side

The server function in `server.ts` is a simpler regex-based parser used as a fallback or cross-reference. It detects the same OS categories but uses slightly different patterns (e.g. it distinguishes `Windows 8.1` via `Windows NT 6.3` and `Windows 7` via `Windows NT 6.1`). On mobile, the server sets the device name directly from the OS detection result.

<Tip>
  Because the client sends its own detected device info with the session open payload, the server's User Agent parsing acts as a safety net for sessions where the client payload is malformed or missing. In normal operation, the values you see in the console come from `detectClientDevice()` on the visitor's browser.
</Tip>
